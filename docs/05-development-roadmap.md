# 开发计划与个人工作记录

已有代码可以降低从零搭框架的成本，但毕业设计仍需要学生亲自理解、验证和改进。下面给出一个可调整的八周计划，不代表学校规定或已经发生的开发过程。

## 1 八周里程碑

| 阶段 | 要完成的动作 | 该阶段留下的证据 | 完成标准 |
| --- | --- | --- | --- |
| 第 1 周 | 与导师确定范围；运行演示；阅读需求 | 任务书、需求编号、首次运行记录 | 能独立启动并完成一轮练习 |
| 第 2 周 | 阅读后端与数据库；画架构和 ER 图 | 数据字典、接口笔记、自己的图 | 能追踪一条题目从生成到错题本 |
| 第 3 周 | 熟悉生成、格式校验与引用验证；补边界测试 | 测试用例、修改记录、失败与修复证据 | 解释无效模型输出为何被拒绝 |
| 第 4 周 | 做一个明确的小改进；不盲目加大功能 | 需求变更、前后版本、回归测试 | 改动可运行且能说明设计取舍 |
| 第 5 周 | 设计真实模型实验；准备合法资料和评分规范 | 数据集清单、实验预登记、预算上限 | 开始实验前确定指标和样本 |
| 第 6 周 | 执行实验和人工评分；记录失败 | 原始响应、评分表、日志、汇总脚本 | 数据能从原始记录重算 |
| 第 7 周 | 写论文初稿并与实现逐项核对 | 初稿、图表源文件、引用表 | 没有不存在的功能和虚构结果 |
| 第 8 周 | 导师修改、打包、复现、答辩演练 | 最终版本、测试报告、演示视频 | 换目录或新环境可按手册重现 |

如果只有四周，把读代码与需求整理合并、缩小扩展范围，优先做完整闭环、真实验证和可解释性。不要以牺牲实验真实性换取表格“好看”。

## 2 读代码的具体顺序

1. 看根目录 README、依赖文件和本指南，知道怎样启动与测试。
2. 看 `app/main.py`，找到页面入口及接口路由，列出每个接口的输入、输出和可能错误。
3. 找配置模块，理解环境变量怎样进入后端。搜索 `API_MODE`、`LLM_API_KEY` 和 `DATABASE_PATH`，确认哪些值对浏览器可见。
4. 找数据库初始化 SQL，画六类核心数据的关系；检查外键与事务。
5. 找生成服务，分别跟踪演示分支和真实 API 分支，记录它们共享哪些校验。
6. 找练习提交逻辑，确认正确答案来自数据库，判分在哪一端发生，重复提交怎样处理。
7. 找错题更新逻辑，明确“掌握”“错题次数”“练习记录”各自含义。
8. 看前端 JavaScript，挑一个按钮，从点击事件跟踪到 fetch 请求，再返回后端对应函数。
9. 看测试，先读一个完整正常流程，再读错误流程。

每一步至少写一段自己的解释。最有效的学习证据是能对一个具体输入预测输出，再运行验证，而非背诵框架定义。

## 3 一次小改动怎样完成

示例目标：让用户在生成题目之前更明确地知道题数限制。这里只是可选改动建议，不代表本版缺陷或已实现功能。

1. 写需求：什么人，在什么操作中遇到什么困难，希望得到什么反馈。
2. 定验收：合法数值可提交；非法数值有清晰提示；后端仍校验，不能只靠前端。
3. 找影响范围：页面输入、JavaScript、请求模型、生成服务、测试与文档。
4. 先写或调整测试，观察修改前的失败原因。
5. 实现最小改动，不同时重构整个项目。
6. 运行完整检查，手动点击页面，包括取消、重复点击和刷新。
7. 更新对应文档、保存截图和提交记录。
8. 用 3–5 句话写“为什么这样改、如何验证、还有什么限制”。

不要把格式化整个仓库、改变量名或换页面颜色单独夸大为研究创新。

## 4 适合本项目的可选扩展

以下均属于新任务，需要自己实现和测试后才能计入成果。优先只选一项。

### 4.1 题目质量人工审核

增加待审核状态，由学习者确认题目是否有误。需要设计审核字段、状态转移、练习选题规则、旧数据迁移和测试。可评估错误题进入练习前被发现的比例。不要说“人工审核自动保证正确”。

### 4.2 更细的学习资料分块与选择

为长资料增加可观察的分块策略、块号和选择规则。对比不同块长带来的上下文覆盖、成本和来源支持变化。只有实际实现了检索步骤后，才讨论对应检索指标；不把简单截断或顺序选块称为向量检索。

### 4.3 复习策略

在现有错题状态基础上增加下一次复习日期。需说明规则来源、计时方式、时区、手动更正和测试。没有长期学习实验时，只验证日程计算正确，不宣称提高记忆保持率。

### 4.4 可访问性与易用性

改善键盘操作、表单标签、空状态、错误恢复及小屏显示。制定具体任务，让取得同意的试用者完成，并记录耗时与失败点。不得收集不必要个人信息或把普通试用包装为正式教育干预实验。

## 5 Git 记录建议

学习 Git 的最小目标是知道某次改动修改了什么、能回到哪个版本。每次完成一个小步骤后检查差异，再提交。提交信息写具体，例如“校验空白资料并添加测试”，不要全部写“update”。

```text
git status
git diff
git add app/ tests/ docs/
git diff --cached
git commit -m "Document and test empty material validation"
```

上述 `git add` 范围只是示例，应按自己的实际文件选择。提交前逐行看暂存差异，尤其检查密钥、数据库、实验原文和截图。`.gitignore` 不能阻止已经被跟踪文件的泄露，也不能替代人工检查。不要盲目执行 `git add .` 后直接推送。

## 6 每周记录模板的用法

复制 [周报模板](templates/weekly-log.md) 到自己的私有工作目录，记录日期、目标、实际完成、问题与下周计划。每项“已完成”附一个证据：提交 ID、测试日志、截图编号或文档版本。

记录也应包括失败：例如某种 PDF 无法提取、某模型经常输出多答案题、某测试暴露重复提交问题。失败记录能帮助论文形成真实分析。

## 7 开发冻结与交付

答辩前保留一个稳定版本，并记录对应提交 ID。冻结后优先修会影响演示和数据完整性的错误。修改后重跑检查，更新演示截图。避免答辩前夜换框架、换数据库或加入没有测试的大功能。

项目代码、数据库、论文、截图和测试报告应指向同一个版本。若论文截图来自旧版，要重新生成或明确说明。
