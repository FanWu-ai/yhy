# 毕业设计交付与学术诚信

## 1 最终交付应包含什么

以学校要求为准，建议至少准备以下可检查成果。

### 1.1 软件与运行材料

- 一个固定版本的源码及版本标识。
- 依赖文件、配置示例与 README。
- 不含密钥的默认演示模式和有权公开的样例。
- 安装步骤、操作说明、已知限制和故障排查。
- 自动测试与所需静态检查。
- 本人环境的实际测试日志，区分通过、失败、跳过和未执行。
- 题库导出样例及经过验证的恢复说明，避免包含个人数据。

### 1.2 学校要求的过程材料

- 导师确认的题目、任务书和开题报告。
- 阶段检查材料与周报。
- 需求、设计、数据库和接口材料。
- 正式论文与学校要求的其他附件。
- 参考文献、图表源文件、必要的外文材料。
- AI 辅助与开源复用说明，按学校规则提交。

### 1.3 答辩与实验材料

- 与代码版本一致的演示 PPT 或演讲提纲。
- 实际操作视频和可离线复现的演示数据。
- 真实 API 实验原始记录、评分规则与人工评分表；未做就明确写未做。
- 统计脚本或可重算表格。
- 失败案例及局限分析。
- 不含秘密的最终演示包。

## 2 公开仓库发布前检查

公开意味着陌生人也可能下载、复制并长期保存。删除当前文件不能保证已经公开的副本消失。推送前逐项检查，而不是发布后再补救。

- [ ] `.env` 和所有真实 API Key 未被跟踪。
- [ ] SQLite 数据库、导出文件、学生成绩、真实错题记录未进入提交。
- [ ] PDF 和课件有明确再分发权限；“我能访问”不等于“我能公开”。
- [ ] 截图没有账号、学号、姓名、邮箱、密钥或私有链接。
- [ ] 日志没有请求头、认证信息和不应公开的原文。
- [ ] 没有私人对话、与项目无关的背景资料或内部工作记录。
- [ ] 没有把个人论文、学校未公开题目或评审意见默认放入公开仓库。
- [ ] 许可证范围清楚；第三方版权声明按各自许可保留。
- [ ] README 明确单人本地原型、演示模式和模型质量限制。
- [ ] 远端文件与本地待交付版本一致，线上检查状态如实记录。

如果误提交了密钥，立即在该密钥的官方服务商控制台撤销并更换；只删除仓库中的字符串不够。不要把新密钥贴到 issue 或群聊里解释问题。

## 3 使用开源项目与毕业设计的关系

代码许可证处理的是授权使用、修改、分发等问题；学校的署名和原创性要求是另外一层要求。即便许可允许使用，也不代表可以把别人的全部工作声称为自己独立完成。

维护一张来源记录：组件或文件、来源、许可证、使用方式、是否修改、自己做了什么。例如 FastAPI 是框架，SQLite 是数据库，模型能力来自服务商。项目代码、AI 辅助代码与自己后来改进的部分也应区分。

如学校要求“独立完成”，应向导师说明所复用的基础，获得明确指导后再决定用法。不以改名、换皮、翻译变量或隐藏来源来规避要求。

## 4 AI 辅助说明怎样写

按真实情况填写，不要套用一段与事实不同的声明。以下仅为内容框架：

“本项目在〔实际阶段〕使用了〔实际工具与版本或使用日期〕辅助进行〔需求梳理、代码草案、测试建议、文字润色等实际范围〕。对采用的结果，作者完成了〔真实进行的理解、修改、测试与核验〕。实验数据来源于〔实际执行过程〕，未以自动生成的数字替代真实测量。第三方代码、文献与工具使用情况按学校规定标注。”

如果某段代码尚未理解，不应声称已独立审核。补齐理解、测试和记录后再完善说明。无需为了说明 AI 使用而公开不相关的私人聊天、个人信息或任何密钥；按学校要求提供与项目直接有关、允许公开的记录即可。

## 5 个人贡献可怎样证明

- 能解释核心接口、数据库关系和关键分支。
- 有逐步修改的版本记录与原因，而非只有最终压缩包。
- 有自己发现的具体问题、复现步骤、修复及测试。
- 有自己设计和执行的评估方案、原始记录与分析。
- 能说明哪些功能没做以及不做的理由。
- 能在答辩中应对小改动或说明修改位置。

代码行数、漂亮页面和文档篇幅都不能代替这些证据。

## 6 交付目录建议

以下是给学校提交材料的本地整理建议，不表示全部应公开到 GitHub。

```text
graduation-submission/
  01-source/
  02-run-guide/
  03-thesis/
  04-process-records/
  05-tests-and-experiments/
  06-defense/
  07-licenses-and-acknowledgment/
```

压缩前排除 `.venv`、缓存、真实配置和没有权限分发的资料。完整实验记录可根据导师要求单独私下提交，公开包只含已授权、去标识的版本。

## 7 最后一次独立复现

1. 从最终提交版本重新下载或复制到一个新目录。
2. 新建虚拟环境并按照依赖文件安装，不复用未知的全局包。
3. 使用演示模式启动，不依赖本机早就配置好的密钥。
4. 完成主要操作流程与检查命令。
5. 核对文档、界面和代码版本一致。
6. 保存这次复现的日期、环境和结果。

如果这一步失败，优先修复运行路径和依赖问题，再提交最终包。确实无法验证的系统或真实 API 条件应明确说明，不承诺任意电脑、任意服务商都能直接运行。
