# 论文写作路线与逐章材料

本章提供写作提纲、证据清单和可改写的表达框架，不提供冒充学生亲自完成的整篇论文。正式写作应使用学校模板，以你的实际开发、实验与理解为依据。

## 1 先确定格式和证据

向导师或教务确认：论文模板、章节安排、字数、引用格式、图表编号、英文摘要、查重要求、AI 辅助使用说明、是否需要外文翻译和附件。没有一个统一的全国模板适用于所有学校。

建立一张“论点—证据”清单：

| 想写的内容 | 必须具备的证据 |
| --- | --- |
| 系统支持某功能 | 对应代码、实际运行截图及测试 |
| 输出校验能拦截某错误 | 构造输入、校验逻辑、失败测试或实验日志 |
| 出题质量达到某比例 | 合法样本、模型版本、原始输出、预定评分规则、评分记录 |
| 相比基线有所改善 | 可复现基线、同等条件、原始数据与比较方法 |
| 操作方便 | 明确任务的试用记录，或谨慎限定为设计目标 |
| 减少复习时间或提高成绩 | 与该因果结论相匹配的实验设计；没有就不写 |

先收集证据再写结论，可以显著减少论文和代码互相矛盾。

## 2 摘要与关键词

摘要一般围绕四个问题：研究的问题是什么，采用什么方法，实现了什么，实际验证得到什么及其范围。长度按学校要求。

写作框架：

“针对〔具体学习资料出题与错题整理问题〕，设计并实现了〔系统名称〕。系统采用〔实际技术栈〕，通过〔实际资料处理方法〕、〔实际模型约束与校验〕和〔练习错题流程〕实现〔已完成范围〕。在〔实际环境与样本〕下开展〔实际验证方法〕，结果显示〔真实结果〕。系统目前的限制包括〔真实局限〕。”

在实验完成前保留占位符，不填“准确率 98%”“运行稳定”等没有数据的结论。英文摘要应忠实对应中文，不擅自增加创新性或结果。

可讨论的关键词：大语言模型；自动出题；错题管理；来源追溯；Web 应用。最终选择应符合学校关键词数量要求，正文中确实涉及。

## 3 第一章 绪论

### 3.1 研究背景与问题

从具体场景写起：学习资料散落、人工整理练习需要时间、直接模型输出存在格式和依据问题。说明本系统面对单人复习的范围，不泛泛宣称重塑教育或替代教师。

### 3.2 相关工作

将资料分成三类阅读：自动出题研究、基于资料的语言生成与来源支持、学习练习与错题管理应用。每类说明研究做了什么、评价了什么、与本项目有什么关系。

本仓库 [参考资料](10-references.md) 中的 Transformer 与 RAG 原始论文只能支持对应技术背景。它们没有直接评估本系统，也不能拿它们的结果替代自己的实验。自动出题的专业研究文献需要继续按实际研究方向检索和阅读，不为了凑篇数生成不存在的作者和期刊。

### 3.3 研究内容与结构

以任务列出：需求与数据设计、资料约束生成、完整练习闭环、软件测试、题目质量评价。最后简述各章。

建议产物：一张问题与研究内容对应表；一张相关研究对照表，列出任务、输入、方法、评价方式、适用限制和真实引用。

## 4 第二章 相关技术

这章只解释后续设计确实使用的技术。避免复制几十页教科书。

- 大语言模型 API：请求、响应、上下文限制、随机性、服务端调用与费用。
- 提示词与结构约束：怎样约束四选一格式、答案字段和来源字段；语法正确与语义正确的区别。
- 资料依据与来源验证：提供资料作为条件，要求原文引用，再检查引用存在性。若没有实现检索，准确表述为资料约束生成；不要把它画成不存在的向量检索系统。
- FastAPI 与请求校验：路由、输入模型、错误响应；不用把框架自动校验写成自己提出的算法。
- SQLite 与事务：数据落盘、主外键、关联和一次提交的原子性。
- Jinja2 与浏览器 JavaScript：页面生成、接口请求、交互状态和安全文本展示。
- pytest 与模拟对象：让测试不依赖收费外部模型，解释模拟测试的边界。

技术定义引用官方文档或原始论文。项目自己设计的规则引用对应代码和设计说明，不强行附无关论文。

## 5 第三章 需求分析

从 [需求文档](01-topic-and-requirements.md) 整理，但要用自己的实际版本改写。

### 5.1 业务流程与角色

角色是本机学习者。本版没有管理员、教师班级、权限审批链，不画不存在的角色。

用例可以包括：导入资料、生成题目、开始练习、提交答案、查看解析、复习错题、查看历史、导出备份。

### 5.2 功能需求

每条需求写输入、前置条件、主要步骤、异常和结果。示例：“真实生成前，用户选定资料并明确同意发送至所配置服务；若未确认，系统拒绝该请求。”

### 5.3 非功能需求

讨论本地可运行、错误可理解、资料可追溯、数据一致性与配置安全。性能阈值若由你设定，应标为目标；完成测试后才能写是否达到。

### 5.4 可行性与风险

说明普通电脑可运行轻量后端，不进行模型训练；真实调用取决于服务商访问与预算；PDF 提取可能丢失结构；本地单人部署不足以支撑公网多用户。

建议图表：业务用例图、主流程图、功能需求表、非功能需求与验收表、范围排除表。

## 6 第四章 系统总体设计

### 6.1 架构

画浏览器、FastAPI 后端、生成适配器、SQLite 和可选外部模型服务。区分演示路径与真实模型路径。把资料外发的信任边界标出来；不要把密钥画在浏览器里。

### 6.2 模块职责

结合实际文件说明配置、资料处理、出题、题库、练习、错题、统计、备份、页面各模块的职责与依赖。若实际组织方式不同，按代码改图。

### 6.3 数据设计

以 [架构文档](04-architecture-and-api.md) 和 SQL 为依据画 ER 图，列出六类核心表的主键、外键、重要字段、约束。特别说明题目与资料、练习与答案、错题与题目的关系。

不要用数据库表名装饰页面，却在论文中描述另一套不存在的 MySQL 表。默认 SQLite 就如实写 SQLite。

### 6.4 接口与状态

挑 3–5 个有代表性的接口详述，其余放附录。建议包括资料导入、生成、开始练习、提交和备份导入。说明请求字段、返回值、异常码和状态变化。

建议图表：系统架构图、模块图、ER 图、核心数据字典、生成时序图、练习提交时序图。

## 7 第五章 系统实现

这一章突出你可以解释的实际代码和取舍，少贴整页源代码。

### 7.1 资料处理

说明支持格式与大小限制，TXT/Markdown 编码、PDF 提取流程、空文字检测。给出一个成功例和一个扫描件失败例。PDF 文字抽取存在阅读顺序和布局等困难，pypdf 本身不是 OCR。[pypdf 官方说明](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)

### 7.2 生成与校验

从选资料到存题逐步说明：选取资料内容、构造系统指令及资料边界、发起请求、解析响应、校验字段、检查答案与引文、保存生成记录。演示路径单列，清楚写出是确定性示例或模板机制，不是本地训练模型。

可以用短伪代码解释关键算法，但必须与实际代码一致；对未知部分先读懂再写。区分“要求模型遵守”与“程序真的检查”。

### 7.3 练习与错题

说明为什么服务端判分；练习题集合如何确定；重复提交如何处理；错题状态怎样更新；历史统计如何计算。用一题答错再复习的实际数据贯穿说明。

### 7.4 异常与安全

说明密钥从哪里读入、是否返回前端、模型请求失败如何展示、导入数据怎样校验、HTML 文本怎样安全显示。不要宣称完成安全认证；如实说明无登录、无生产级隔离等限制。

### 7.5 界面

选 5–7 张真正由本版运行生成的截图：资料、生成结果、练习、反馈、错题、历史统计、导入导出。截图删去密钥、真实姓名和隐私。每张图说明一个设计目的，避免堆满无解释截图。

## 8 第六章 测试与评价

按 [实验方案](06-testing-and-experiments.md) 分为软件测试和模型评价。

1. 环境与代码版本：操作系统、硬件、Python、依赖、提交 ID、执行日期。
2. 功能和异常测试：输入、预期、实际、结论；失败修复及回归结果。
3. 模型实验设置：资料来源、范围、模型、参数、请求次数、评分者和规则。
4. 结果：原始计数、比例、延迟和费用；区分失败、有效输出与可用题。
5. 失败案例：错误答案、引用片面、多解选项、资料不足或网络错误。
6. 有效性威胁：样本数量、资料代表性、评分主观性、模型版本漂移、题目间相关性。

没有真实模型实验时应明确说明，本章不能拿演示题质量替代。若学校要求真实实验而尚未完成，应完成后再提交。

建议图表：测试环境表、需求测试追踪表、失败分类图、各质量维度分布图、请求延迟分布、原始计数汇总。图表从真实 CSV 重算，不手工编造。

## 9 第七章 总结与展望

总结必须回答第一章提出的问题，并限定结论适用范围。分开写已完成、发现的问题、尚未完成。未来工作可以包括长文资料检索、题目审核、多题型和多人使用，但不能用未来计划掩盖核心需求未实现。

不要写“全面解决幻觉”“显著提升学习效果”“具有广泛推广价值”，除非确有匹配证据。更可靠的写法是：系统完成了哪些流程，在已测条件下呈现哪些特征，还受哪些限制。

## 11 引用和改写

阅读后用自己的理解概括，保留来源。直接引用按学校规则标注，图表转载需要核对版权许可。引用管理工具可辅助整理，但作者、题名、年份、链接与文内对应仍要人工检查。

不要把 API 文档当作同行评审实验论文，不要引用自己没有看过的“二手参考文献列表”。文献不能支持的主张应删去或调整。

## 12 提交前逐句检查

- 每个“实现了”都能指出代码与演示。
- 每个数值都能追到原始记录。
- 每个“提高、降低、优于、显著”都有公平比较或删去。
- 题目、摘要、正文、代码的系统范围一致。
- 技术栈、数据库和模型名称未沿用别人的模板。
- 本人工作、复用代码和 AI 辅助范围如实说明。
- 未把本指南模板或写作建议伪装成实验事实。
